# YapNPlay — Phase-wise Project Report (Proof of Concept)
Status: plan, restructured on 15 October 2026 into category-based phases. Working title: YapNPlay (final name undecided). Android package: com.kglabs28.YapNPlay.
## How to use this report
- Order. Phases are sorted by dependency, the way Kahn's algorithm orders a graph: phases with no dependency come first, and every later phase depends only on phases above it. Do not start a phase until every phase listed under 'Depends on' is finished.
- Categories. Every phase belongs to exactly one category. Open one chat per category and come back to it with that category's next phase. In a category's first message paste the Project brief (next section) and the phase; for later phases in the same chat paste only the phase.
- Self-contained phases. Each phase is written as a prompt: goal, why it matters, requirements, steps, expected tests and done criteria. Hand the text to an AI agent as it stands.
- Complete in one go. A phase is finished only when all its tests pass and its 'Done when' list holds. There are no half-finished phases.
- Factory principle. Components are built independently and assembled at the end. Android screens run on fake data and on the local game engine until the real server is connected in later phases; the last phase assembles everything.
- Shared contracts. The message formats and game contract created in Phase 1 are changed only in the Foundation chat. Tell the other chats when the contract version changes.
- Habits. Commit to git after every working step. Every phase ends with a handoff note (what was built, where it lives, how to run it, known gaps) that you paste into later chats.

## Project brief (paste at the start of every category chat)
What we are building. A private social space for people who already know each other: friends, cousins, relatives. A persistent room holds its members, voice chat stays open, and games are played inside the room. Spectators are first-class: anyone not playing can watch, listen and talk, so nobody feels left out. The first game is Ludo. Later games (card games, drawing games) must plug into the same platform without rewriting it. UNO and Pictionary are third-party trademarks, so future games get original names and art.
Proof-of-concept (POC) goal. A working version the family installs and plays, to answer one question: is gathering in a voice room and playing Ludo together good enough that people come back? The POC may look rough, but it must be correct where changes are expensive later: server authority, stable seats, versioned messages and the voice lifecycle.
The person you are helping. An experienced Android developer on a Windows laptop with no backend or game-development experience, who works with several AI tools. Explain every new term at first use, never use unexplained abbreviations, give numbered steps with exact Windows commands and the expected output, say what to do when something fails, state trade-offs, and give honest feedback. Teach the principle before the code; use code to illustrate.
In the POC. Guest identity with an editable display name; create a room and join by six-character code; lobby with online members, leader, ready status and a ten-second countdown; voice in the room (microphone off and speaker on by default; spectators can talk); Ludo for 2 to 4 players with the server deciding dice and moves; 30-second turn timer with automatic play; reconnection; spectating a running match; removal of away players; final ranking; landscape only; phones and tablets.
Not in the POC (but design so they can be added): public matchmaking (Game Zone); friends and invitations; replacement invitations for away players; room house-rule toggles; leaderboards and history; other games; login providers such as Google; ads; iPhone, web and desktop; push notifications; Hindi; early-close voting and points.
Confirmed decisions.
- Android first: Kotlin, Jetpack Compose, landscape only, Android 8 or newer, English only (all text in resources so Hindi can follow). Dependency injection with Koin. Clean architecture, repository pattern, SOLID principles, use cases where real logic exists, and MVI (Model-View-Intent: one immutable screen state, user actions as intents, one-way data flow). Code stays friendly to Kotlin Multiplatform (sharing Kotlin across platforms); one module per game.
- Backend: Kotlin with Ktor. The server is the authority for everything that matters.
- Voice: LiveKit first, hidden behind our own interface so a provider swap touches one implementation and one binding.
- Identity: guest accounts. Each user has a permanent, unique, system-generated ID and a display name that can change and need not be unique. Login providers attach later to the same ID. A guest account is lost on uninstall.
- Rooms: up to 10 members; join by six-character code with no approval; membership persists while offline; if the leader disconnects, leadership passes to the member present longest. The leader manages the room but gets no gameplay advantage.
- Match start: Ludo needs 2 to 4 players; if more than four are ready, the first four to press ready get seats and the rest spectate; the server assigns seat numbers and colours randomly; ten-second countdown that any eligible player can cancel.
- Ludo rules (traditional; fixed for public matches, toggles inside private rooms later): four pieces each; a piece leaves base on a 6 only; a 6, a capture and a piece reaching home each give an extra turn (a 1 gives none); the third six in a row is forfeited (nothing moves, the turn passes); an exact roll is needed to finish (smaller rolls move a piece closer, larger rolls cannot move that piece, and if no piece can move the turn passes); landing on a lone opposing piece sends it to base; each colour's start square and the star squares are safe; two or more same-colour pieces on one unsafe square are protected (an opponent may land there but captures nothing and gets no extra turn, and a landing piece captures only a lone opposing piece sharing that square); when a protected pair breaks and an opposing piece stands on that square, the piece left behind goes to base and the opponent gets no extra turn; no blocking.
- Timers and removal: 30 seconds per turn; at timeout the server plays the best computer-style move (automatic play) and counts a missed turn; a valid action resets the count. Each game declares its own timing values; Ludo waits only 5 seconds when a disconnected player's turn arrives. A seat is 'away' after three consecutive missed turns or 60 seconds of continuous disconnection. In the POC an away player and their pieces are removed from the board immediately, through one hook (the replacement policy) where the replacement-invitation flow will later be inserted; the removed user stays in the room as a spectator. Reconnecting before removal restores control; after removal the user only spectates.
- Match end: the match runs until one player is left; finishing order gives places; if everyone else is removed the sole remaining player ranks above removed players and the match ends; if everyone is removed the match is cancelled; removed players rank last, later-removed above earlier-removed. Later: a leader-proposed early close that all players must accept, with points by position.
How the system works. The server owns identities, rooms, membership, leader, readiness, countdown, seat assignment, dice, legal moves, timers, automatic play, removals, results and the event log; the app owns drawing, local screen state, microphone and speaker choices and sending requests, and never computes outcomes. One WebSocket (a connection that stays open so both sides can send at any time) per user carries two logical channels: the room channel (who is here, ready, leader, countdown) and the match channel (game events). Voice is a separate connection to the voice provider and follows the room, not the match. Every client request carries a request ID so duplicates are ignored; the server answers with complete state snapshots carrying version numbers, and deadlines travel as absolute server times plus the server's current time. Each match has one actor: a single worker that owns the match data and receives every event through one queue, so simultaneous events become ordered events. Clock and randomness are injected so tests are deterministic. Modules: :shared:protocol, :shared:game-api, :games:ludo, :server, :app.
## Engineering rules for all code
- No hardcoded values. Text lives in string resources; sizes, colours and durations are named design tokens; numbers with meaning (code length, limits, timeouts) are named constants kept in one place per module; server settings come from environment variables.
- Tests ship with the feature. Many unit tests, some integration tests, and UI flow tests for every screen. A feature without tests is not done.
- Small, single-purpose classes with dependencies injected. Put an interface only where something is likely to change (voice provider, transport, storage) or must be replaced in tests.
- Time and randomness are injected, never read directly inside game or timer logic.
- Typed errors, never error strings; no silent failures; logs never contain secrets.
- Secrets (keys, tokens, passwords) never go into code or git.
- Adaptive by default. Layouts adapt to window size; nothing is sized for one phone.
- Teach as you build. The agent explains what each step does and why before the user runs it.
## Phase 1 — Workspace, repository and shared contracts
Category: FOUNDATION. Depends on: nothing.
Prompt to the agent. You are the contract owner for YapNPlay (see the Project brief). Create the workspace and the shared contracts that every other category builds against. The user has never set up a multi-module Gradle project (Gradle is the build tool; a module is a separate build unit), so teach each step.
Why this phase matters. The Android app, the server and the game engines are built by different agents at different times. They can only be assembled at the end if they agree on message formats and the game contract from day one. A mistake here is expensive; a clean contract keeps every later phase independent.
Requirements and setup (teach first).
- Install the latest stable Android Studio (it bundles a JDK, the Java Development Kit that builds Kotlin) and Git for Windows. Verify with git --version.
- Create the folder C:/dev/YapNPlay, not inside Desktop, Documents or OneDrive, because file syncing disturbs builds.
- No accounts are needed in this phase.
Steps.
- Workspace: folder layout (shared, games, server, app, docs); git init; a .gitignore suitable for Gradle, Android Studio and secrets files; first commit.
- Root Gradle project with Kotlin build scripts, a version catalog (one file listing every library version) pinned to stable versions of Kotlin, kotlinx.serialization, kotlinx.coroutines, kotlinx-datetime and the test libraries. settings.gradle.kts includes :shared:protocol and :shared:game-api now; later phases add :games:ludo, :server and :app with one include line each.
- Both shared modules are plain Kotlin libraries using only Kotlin and kotlinx libraries, never java.* classes, so they can become Kotlin Multiplatform later.
- :shared:game-api contents: identifiers (UserId, SeatNumber starting at 1, PieceId, GameId); Viewer (a Player with a seat, or a Spectator); Action (RollDice, MovePiece(pieceId)); GameEvent as a sealed family; TimingConfig (turnSeconds 30, disconnectedWaitSeconds, awayAfterMisses 3, awayAfterDisconnectSeconds 60); GameRandom (an interface that returns random integers, so tests can fix it); MatchOutcome (ranking of seats with status FINISHED or REMOVED); and the Game interface: id, timing, minPlayers, maxPlayers, defaultRules(), start(rules, seatCount, random), apply(state, seat, action, random) returning new state plus events or a typed rejection, currentActor(state), autoplay(state, seat), removeSeat(state, seat), viewFor(state, viewer), isFinished(state), outcome(state). Engines must be pure functions: no clock, network or hidden randomness.
- :shared:protocol contents. Envelope: requestId (UUID text), channel (ROOM or MATCH), type, payload. Room channel, client to server: CreateRoom(name?), JoinRoom(code) (also used to re-enter a room you already belong to), LeaveRoom (give up membership), ExitLobby (stay a member but stop being present), SetReady(ready), StartCountdown, CancelCountdown, RequestSnapshot(lastVersion). Room channel, server to client: Ack(requestId), Rejected(requestId, code, message), RoomSnapshot(version, serverTime, room: id, code, name, leaderId, members[userId, displayName, presence ONLINE or OFFLINE, ready], selectedGame, countdownDeadline?, matchInProgress?(matchId)), MatchStarting(matchId). Match channel, client to server: RollDice(matchId), MovePiece(matchId, pieceId), RequestSnapshot(matchId, lastVersion). Match channel, server to client: MatchSnapshot(matchId, version, serverTime, viewer role and seat, seats[seat, colour, controllerUserId, status ACTIVE or REMOVED, connected, autoPlay, consecutiveMisses], public game state, legalMoves for the acting seat, turn: seat, phase, deadline), MatchEvent(version, event), MatchEnded(ranking). Error codes: NOT_AUTHENTICATED, NOT_FOUND, NOT_MEMBER, NOT_LEADER, ROOM_FULL, INVALID_CODE, ALREADY_IN_ROOM, NOT_ENOUGH_READY, STALE_VERSION, NOT_YOUR_TURN, ILLEGAL_MOVE, MATCH_ENDED, RATE_LIMITED, BAD_REQUEST. HTTP bodies: GuestCreated(userId, secret), Me(userId, displayName), UpdateName(displayName), MyRooms(rooms[roomId, code, name, memberCount, onlineCount]), VoiceToken(url, token, expiresAt). Connection rule: the WebSocket is opened at /ws with an Authorization bearer header made of userId and secret; for browser-console testing a development-only query parameter is accepted.
- Architecture rules file docs/ARCHITECTURE_RULES.md: layers, which module may depend on which (shared modules depend on nothing; engines depend on game-api; server and app depend on shared modules; the server never depends on the app, and the app never depends on the server), naming, test rules, the engineering rules of this report, and instructions every AI agent must follow (read the rules first, restate the plan, never edit shared modules, ask when unsure). Copy this report into docs/.
- Contract versioning: a ContractVersion constant starting at 0.1.0; the rule that any change to a shared module bumps it and is announced to all chats.
Test cases.
- Every protocol message serialises to JSON and back unchanged (round trip); unknown extra fields are ignored; a missing required field is rejected.
- Golden files: one stored JSON example per message in the protocol test resources; the tests fail if serialisation drifts from them.
- A fake Game implementation in the game-api tests proves the interface is usable (start, apply, autoplay, removeSeat, viewFor).
- A dependency test or check proves the shared modules import nothing from java.* or Android.
- The command gradlew.bat build run from the root succeeds from a clean checkout.
Done when. The root project builds with one command; all contract tests pass; the rules file and this report are in docs; the git history has meaningful commits; the user can explain in their own words why the server decides and the app only displays.
Future expansion. More games add their own module that implements the Game interface; new message types are added with a version bump; replacement-invitation messages join the match channel later.
Handoff. The list of contract types, the version, how to run the build, and the process for proposing a contract change.
## Phase 2 — Visual identity and design system
Category: DESIGN. Depends on: nothing.
Prompt to the agent. You are a senior mobile product and game UI designer. YapNPlay is a landscape-only Android app where friends, cousins and relatives gather in a private room with voice chat and play Ludo together (see the Project brief). Create the visual identity and design system that every later screen design and the Android theme will be built from. Everything must be specified as exact values (hex colours, dp and sp sizes, millisecond durations) so developers never guess.
Why this phase matters. Consistent tokens (named values) let different AI agents and tools produce screens that look like one product, and let the Android phase build the theme from a list instead of from pictures. The layout rules here make the app rearrange itself on tablets.

Randomness arrives through the GameRandom interface.
Board and state model.
- Track: 52 shared squares indexed 0 to 51 clockwise. Colour start squares: red 0, green 13, yellow 26, blue 39. Safe squares: the four start squares and the four star squares at 8, 21, 34 and 47.
- Piece progress: -1 in base; 0 to 50 on the shared track, counted from the piece's own start square (absolute square = (start + progress) mod 52); 51 to 55 in its private home column (five squares); 56 finished. All numbers live as named constants in one file and are covered by tests; the user will confirm them against a real family board in a walk-through.
- Colours by player count: 2 players use opposite colours; 3 or 4 players use any three or all four. The server picks seat numbers and colours randomly; the engine receives them.
- Match state (serialisable with kotlinx.serialization): rules config, seats (number, colour, four pieces' progress, status ACTIVE, FINISHED or REMOVED), current seat, phase (AWAITING_ROLL, AWAITING_MOVE with the roll and the legal pieces, or FINISHED), consecutive-sixes counter, finishing order, removal order, turn counter.
- Rules config (data, not code): baseExitRolls (default {6}; a private-room toggle later sets {1, 6}), extraTurnOnSix, extraTurnOnCapture, extraTurnOnHome (all true), threeSixesForfeit (true), pairProtection (true), exactFinish (true), autoMoveWhenSingleOption (false). The public default is the traditional set from the Project brief.
Rules to encode (all confirmed rules from the brief), plus assumptions the agent must list for the user's approval before coding. Assumptions to confirm: (a) a 6 with no legal move passes the turn without an extra roll; (b) with exactly one legal piece the player still chooses it (the app may offer one-tap confirm); (c) the consecutive-sixes counter counts rolls by the same seat in a row and resets when the turn passes to another seat; (d) captures happen only on the shared track, never in the home column; (e) a lander captures every lone opposing piece on a non-safe square, once, with a single extra turn; (f) a protected group of two or more same-colour pieces is never captured; (g) when a group drops to one piece and an opposing piece is on that square, the remaining piece goes to base with no extra turn for the opponent.
Steps. (1) Create the module and a docs/ludo-rules.md with numbered rules and worked examples; get the user's approval of the assumptions. (2) Board constants and geometry functions with tests. (3) State, actions and legal-move generation. (4) apply(): rolling (three-sixes forfeit), moving, exact finish, capture, pair protection and pair break, extra turns, turn passing. (5) removeSeat(), finishing order and outcome(). (6) autoplay(). (7) viewFor() (Ludo has no hidden information, so every viewer gets the same public state; spectators receive an empty legal-move list). (8) Event stream for the UI and the event log. (9) Simulation and property tests. (10) A short README for the module.
Events emitted (for animations and the log). DiceRolled(seat, value); PieceMoved(seat, piece, fromProgress, toProgress, squares passed); PieceCaptured(by, victim, piece, reason CAPTURE or PAIR_BROKEN); PieceFinished; ExtraTurn(reason); TurnForfeited(THREE_SIXES); TurnPassed(NO_LEGAL_MOVE or NORMAL); SeatRemoved; SeatFinished(place); MatchEnded(ranking).
Automatic play (what the server does when a player's time runs out). If a roll is needed, roll. Otherwise choose the legal move with the highest score: finishing a piece (1000), capturing (800 plus the victim's progress), leaving base (600), landing on a safe square or forming a protected pair (400), then the piece furthest along; ties go to the lowest piece number. Deterministic and always legal.
Ranking and removal. Finishing order gives places. A removed seat's pieces disappear from the board; if it was the current seat, play passes on. If one active seat remains the match ends: that seat ranks after the finishers and above removed seats; removed seats rank last, later-removed above earlier-removed; if every seat is removed the outcome is CANCELLED.
Test cases.
- Geometry: 52 distinct squares; progress-to-square mapping for each colour; safe-square set; home-column length; leaving base places a piece at progress 0.
- Rolls: leave base only on 6 (and on 1 or 6 when configured); a piece 3 steps from home finishes on 3, moves on 1 or 2, cannot move on 4 to 6; no legal move passes the turn.
- Extra turns: after a 6, a capture and reaching home; none after 1 to 5; chains; sixes 6, 6, 6 forfeit the third with no movement; counter resets on a non-6 and on turn change.
- Capture: lone opposing piece captured and sent to base; not on safe squares or in the home column; own pieces never captured; mover gets one extra turn.
- Pairs: red pair and blue lands (coexist, no capture, no extra turn); red pair plus lone blue and yellow lands (only blue captured); red pair breaks with blue present (remaining red to base, blue gets no extra turn); pair of three drops to two (still protected); pair formed by a second piece landing; pairProtection off makes captures normal.
- Removal and end: removing the current seat passes the turn; removal order ranking; sole remaining seat ranks above removed; everyone removed gives CANCELLED; finish order and last place assignment.
- Autoplay: constructed states prove each priority; ties are deterministic; the action returned is always legal.
- Determinism: same seed and actions give identical states and events; state survives a serialise-and-restore in mid-game.
- Simulation: 10,000 seeded games with 2, 3 and 4 seats, autoplay for everyone and random removals; every game ends within a turn cap; after every action the invariants hold (piece counts constant, progress values in range, exactly one current seat, no two different colours on one unsafe square except as the pair rule allows). Fuzz: random illegal actions are rejected with typed errors and never change the state.
- Walk-through: scripted scenarios from the user's family examples, checked by the user against a physical board.
Done when. All tests pass; the simulation runs 10,000 games in under 20 seconds; the rules document and assumptions are approved by the user; the module exposes only the Game implementation, rules config and state types.

## Phase 10 — Match service (Ludo matches on the server)
Category: BACKEND. Depends on: Phases 1, 5 and 6.
Prompt to the agent. You are a senior backend engineer and a patient teacher. Why this phase matters. This is the part of the product that must be correct under disconnects, races and cheating attempts. The Android client only displays what this service decides.
Requirements. The Phase 6 server and database running; no accounts.
What to build (in this order, each with its tests).
- Migrations: matches (room, game, frozen rules snapshot, status, version, state snapshot, timestamps); match_seats; seat_controllers (seat, user, from, to, reason); match_participation (user, role PLAYER or SPECTATOR, consecutive misses, connection timestamps); match_events (sequence number, type, payload, time).
- A MatchStarter implementation replacing the Phase 6 stub: freezes the rules snapshot (the public default set), assigns seat numbers and colours randomly with the injected random among the first four ready members, stores the initial state, marks the room as having a match in progress, and sends MatchStarting with the real match ID. Everyone else in the room becomes a spectator.
- A MatchActor per match (one worker, one inbox queue). Inbox messages: PlayerAction, TimerFired, Disconnected, Reconnected, SpectatorJoined. Validation chain for every action: identity from the connection only; the user controls the acting seat; it is that seat's turn; the match is active; the request ID is new; the client's version is current. Then the engine applies it with the server's random (a client can never supply a dice result), the event and a snapshot are saved in one database transaction, and per-viewer snapshots are broadcast (spectators receive an empty legal-move list).
- Timers as deadlines stored in match state: a turn deadline of now plus the game's turn seconds (30 for Ludo); if the acting seat is disconnected, only the disconnected wait (5 seconds). On expiry the engine's autoplay acts and the seat's consecutive-miss counter rises; any valid player action resets it. A seat becomes away at three consecutive misses or 60 seconds of continuous disconnection; connection state and miss count are tracked separately. Away calls ReplacementPolicy.onSeatEligible, whose default removes the seat immediately (engine.removeSeat); the removed user becomes a spectator. Document this hook as the place where the replacement-invitation flow will be inserted later.
- Reconnection: a user reconnecting before removal regains control of the same seat and a fresh snapshot; after removal they only spectate; a second device replaces the first connection; stale or old requests are rejected. Any room member who is not a player can request a match snapshot and watch, including people who join mid-match.
- Match end: the engine's outcome produces MatchEnded with the ranking; results are saved; the room returns to the lobby state with ready flags reset; if every seat is removed the match is cancelled.
- Crash recovery: at startup load active matches, rebuild actors from the last snapshot, re-arm timers from stored deadlines (overdue ones fire immediately, in order).
- Event log: every applied action, timer, disconnect and removal is appended with a contiguous sequence number; a development-only endpoint lists a match's events.

- Authority: a wrong user, a spectator or an out-of-turn user cannot act; an illegal move gives ILLEGAL_MOVE and leaves the state unchanged; a client-supplied dice value is ignored; a duplicate request ID applies once; a stale version is refused.
- Timers: 30 seconds of silence triggers autoplay and a counted miss; a valid action resets the count; three misses remove the seat; a disconnected seat waits 5 seconds on its turn before autoplay; 60 seconds of continuous disconnection removes the seat; reconnecting before removal restores control; reconnecting after removal gives a spectator view; connection state and miss count never get mixed.
- Races: a move and the timeout at the same virtual instant produce exactly one outcome; a double-submitted move applies once; a disconnect during the player's own turn and a removal while a roll is pending resolve consistently.
- Spectators: joining mid-match gives the same public state; they never receive controls; counts update.
- End states: normal finish ranking; sole remaining player; everyone removed gives a cancelled match; the room returns to the lobby with ready flags cleared.
- Recovery: stopping and restarting the server mid-match resumes the same state and deadlines; overdue timers fire in order.
- Consistency: all clients' snapshots match at the same version, per their viewer rules; replaying the event log reproduces the final state.
- Load sanity: 50 simultaneous simulated four-player matches finish in virtual time with stable memory.

- Flows: MatchStarting in the lobby opens the game screen with the viewer's role; 'Watch' from the lobby opens the spectator screen; a removed player gets the overlay and becomes a spectator; MatchEnded shows the result and returns to the lobby; reconnect after backgrounding or a network drop fetches the room snapshot and then the match snapshot; SessionReplaced is handled; Rejected codes (NOT_YOUR_TURN, ILLEGAL_MOVE, STALE_VERSION, MATCH_ENDED) map to calm messages.
- The local source stays available behind a debug switch for demos.

## Glossary
- MVI (Model-View-Intent): one immutable state per screen; user actions are intents; data flows one way.
- KMP (Kotlin Multiplatform): sharing Kotlin code between Android, iPhone, web and desktop.
- Gradle module: a separate build unit; one cannot use another unless declared. Version catalog: one file listing all library versions.
- WebSocket: a connection that stays open so server and app can send at any time. Snapshot: the complete current state sent in one message.
- Actor: one worker that owns some data and handles events one at a time from a queue. Idempotent: repeating the request has no extra effect.
- Design token: a named design value (a colour, a size, a duration). Layout tier: S, M or L window size class used to rearrange screens.
- LiveKit: a service that relays real-time audio between devices. Access token (JWT): a signed short-lived pass to join one voice room.
- Docker container: a program packaged with everything it needs, run in isolation. Migration: a versioned database change.
- SSH: secure remote command line. TLS certificate: what makes https and wss secure. Reverse proxy: a front door server (Caddy) that forwards requests to the app.
- Robolectric: runs Android UI tests on the laptop without an emulator. APK: the installable Android file.
